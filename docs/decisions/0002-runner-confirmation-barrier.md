# Runner 中的严格动作确认屏障

## 状态

已接受（2026-07-27），补充动作前屏障（2026-07-28）

## 决定

动作派发后的 **AFA 委托动作**确认循环属于 `repl-app::Runner`，不下沉到 `repl-core::Machine`。Runner 在每个动作
派发前记录最新尺子样本的 `min_frame_id`，随后只接受 `frame_id > min_frame_id` 的新样本。
确认窗口只允许暂停态：战斗状态归一化后的任何 `is_running=true` 样本立即失败；这里不能把
`Snapshot::is_running`（费用条识别管线状态）误当成战斗运行态。`0.2x_paused` 只能等待；
动作只有在目标绝对帧收到可信 `1x_paused` 样本后才算完成。

动作派发前原有的稳定等待也属于 Runner 的尺子屏障，不能只是休眠后继续使用 Machine 游标。
Runner 必须在完整稳定期持续读取尺子，并在实际输入前以最新样本复核：只有目标绝对帧的可信
`1x_paused` 才允许派发；运行态、离战、倍速不符或目标帧不一致都在任何输入之前失败。通过该
屏障的样本 `frame_id` 同时作为派发后确认的 `min_frame_id`。运行期 UI 的绝对帧也直接来自尺子，
Machine 游标只服务状态机控制，不再覆盖用户看到的尺子读数。
部署识别和坐标计算可能发生在 Runner 屏障之后，因此 Session 必须接受一个最终输入守卫，在首个
部署拖拽或 AFA 热键发出前再次读取尺子；准备期间新到达的样本也必须纳入同一判定。

## 原因

Machine 是纯逻辑状态机，没有尺子访问权；Runner 已经持有尺子客户端和等待逻辑，把阻塞确认放
在 Runner 可以保持 Machine 的命令接口纯粹。新样本水位避免同帧多动作复用上一动作的快照；拒绝
运行态避免游戏在确认采样前越过目标帧后仍被错误确认。
同理，动作前屏障避免尺子在稳定等待期间已经越过目标，而 Runner 仍按旧 Machine 游标派发输入。

## 后果

- 确认超时、运行态、离战、倍速不符或尺子异常都会中止本次复刻，不补发热键。
- `Finish` 不发送暂停或恢复输入；最后一个动作必须自己留下可验证的暂停状态。
- 逐帧 `pulse()` 的内部收尾仍可使用 `1x_running → 1x_paused` 过渡；该过渡不属于委托动作确认窗口。
- 单元测试必须覆盖运行态拒绝、`0.2x_paused` 过渡、新样本水位和可信 `1x_paused` 目标帧。
- 单元测试必须覆盖动作前 Machine 游标仍为目标帧、尺子最新帧已经领先时禁止派发。
- 单元测试必须覆盖 Runner 屏障通过后、Session 准备动作期间尺子继续前进时仍禁止实际输入。
